# KEP-5866 backend qualification (M4 research)

[KEP-5866](https://github.com/kubernetes/enhancements/blob/master/keps/sig-api-machinery/5866-server-side-sharded-list-and-watch/README.md):
server-side sharded LIST/WATCH. Clients send
`?shardSelector=shardRange(field, hexStart, hexEnd)` (CEL
grammar over `object.metadata.uid` / `object.metadata.namespace`);
the API server filters at the source so each replica receives
only its hash range. Status at time of writing: `implementable`,
alpha behind the `ShardedListAndWatch` feature gate. Beta
criteria include informer/reflector framework support.

## Why it matters to shardkit

The M1 architecture pays the "full stream" penalty the KEP
exists to remove: every manager holds a full cache *and* the
gate does direct (`APIReader`) reads per evaluation, so N
tracks × full object streams cross the wire. A KEP backend
would let each track watch only its owned hash range.

## Fit analysis

1. **Coordination stays client-side by design** (KEP non-goals:
   no coordination, no resharding). The gate/observer handshake
   (S1–S11), leases, budgets, and the S7 fence are unaffected —
   the KEP only shrinks the stream. A backend flag would change
   watch construction, never the safety protocol.
2. **Hash alignment is open.** Shardkit partitions on FNV-1a-64
   over the namespace *name* into 1000 buckets plus a sliding
   window; the KEP hashes `object.metadata.namespace` with its
   own function over hex ranges. Adopting it means mapping
   (weight, window, seed) → hex ranges per transition and
   proving the mapping preserves the one-owner property —
   that proof does not exist yet.
3. **Ranges move every transition.** Ownership is recomputed
   per epoch/weight change, so watches would be re-established
   per handoff step. Reshard churn during Active rollouts needs
   measuring (the M4 scale numbers give the baseline: a 10k
   sweep is 0.25 ms CPU, so re-list cost, not CPU, dominates).
4. **Consumer support is the gate.** controller-runtime has no
   sharded-informer support until the KEP's beta criteria land;
   hand-rolling reflector wiring against an alpha API is
   version-skew risk the project already rejects elsewhere
   (cf. webhook limit 4).

## Qualification verdict

Research complete; **no backend flag yet**. Implement behind a
flag when ALL hold: (a) KEP reaches beta with informer support,
(b) the namespace-hash mapping is specified and the one-owner
proof extends to hex ranges, (c) re-list churn is measured
against the M4 baselines on a gate-enabled server. Until then
the client-side partition stands — its cost is measured
(`docs/traces/m4-scale.md`), not assumed.
